# 共用步驟

`docs/spec/` 的 feature 檔由 `tests/test_spec.py` 直接執行。`tests/steps/` 下每個模組
的步驟定義，對**所有**領域的 feature 都看得見；這個資料夾放的是跨領域共用的步驟，
各領域自己的步驟放在 `tests/steps/<領域>/`。

共用步驟是公開介面：之後的 task 只能新增步驟，不能改既有步驟的意義。要改時先改
這份文件與設計（`docs/tasks/skeleton-and-sign-in/design.md` 第 11.3 節），並在 trail
記一列。

## 怎麼設計出來的

先把 31 個 feature 檔的每一句步驟列出來（本文件最後的清單，由程式產生），把引號裡
的值、`<…>` 與數字拿掉後歸成句型，再看哪些句型跨領域重複。跨兩個以上領域的句型
裡，下面這幾類是「不論哪個領域，意思都一樣」的，做成共用步驟：

- 時鐘：`the clock is "…"`（有沒有 `in Asia/Taipei` 都是同一個意思）。
- 登入狀態：`"…" is signed in`（`Given`）。
- 結果：`the request is rejected as …`、`the outcome is …`，可接 `with message "…"`。
- 寫入：`nothing is written`、`nothing else is written`、`no audit row is written`、
  各種 `audit row` 的說法。

其餘跨領域的句型（例如 `payroll is calculated`、`"…" archives "…"`、
`the report is saved as PENDING`）是某一個領域的動作或狀態，被別的領域借用；它們由
擁有那個動作的領域定義一次（步驟對所有 feature 都看得見），不放在這裡。

## 一個 scenario 從哪裡開始

每個 scenario 開始前，`world` fixture 載入 `docs/spec/background.md` 的共用背景：時鐘
設為背景寫的時刻，建立背景表格裡的帳戶（密碼都是 `tests.support.world.PASSWORD`）。
背景是從那份文件解析出來的，不另外抄一份；背景多了一個沒有人會載入的步驟時，
scenario 會失敗而不是默默略過。

`World`（`tests/support/world.py`）是步驟之間共用的狀態，也是各領域的步驟送出請求的
唯一途徑：

| 用法 | 意義 |
| --- | --- |
| `world.sign_in(name)` | 以該帳戶登入（走真的登入頁），記下它的 session |
| `world.prepare(method, path, …)` | 以訪客身分送出佈置場景用的請求（給 `Given`）：不算 scenario 的請求，回應不被斷言，它寫入的東西算在「請求之前」 |
| `world.send(method, path, actor=None, …)` | 送出 scenario 的請求。`actor` 是已登入者的名字，不給就是訪客。第一次呼叫之前的資料庫內容，就是「寫入」的比較基準。拒絕以 JSON 回來（`Accept: application/json`） |
| `world.open_page(path, actor=None)` | 像瀏覽器一樣看一頁（HTML），用來查看請求造成的結果；不算 scenario 的請求 |
| `world.responses` | `send` 得到的回應，依序 |
| `world.changes()` | 請求之後資料庫的全部差異（`tests/support/recorder.py`） |
| `world.accounts[name]` | 背景表格裡那個帳戶的那一列，外加 `id` |
| `world.clock` | 測試時鐘：`set(時刻)`、`advance(minutes=…)` |

規格規定一個 scenario 只有一個 `When`。一個 `When` 可以送出多個請求（例如「任何受
保護的動作」）；這時結果的斷言對每一個回應都要成立。

## 步驟與它們的意義

| 步驟 | 關鍵字 | 意義 |
| --- | --- | --- |
| `the clock is "<時刻>"`、`the clock is "<時刻>" in Asia/Taipei` | Given | 把測試時鐘設為這個時刻（`YYYY-MM-DD HH:MM` 或加上 `:SS`，Asia/Taipei） |
| `"<名字>" is signed in` | Given | 以該帳戶建立登入狀態；之後 `world.send(…, actor="<名字>")` 帶著它 |
| `the request is rejected as <類別>` | Then | 每個回應的 HTTP 狀態碼（取自 `docs/spec/conventions.md` 的表）、`X-Outcome` 標頭與主體的 `outcome` 都是這個類別 |
| `… with message "<訊息>"` | Then | 同上，而且主體的 `message` 與這段文字逐字相同 |
| `the outcome is <結果>`、`… with message "<訊息>"` | Then | `<結果>` 是結果類別時，同 `the request is rejected as`；是 `accepted` 時，每個回應的狀態碼都小於 400 而且沒有 `X-Outcome`；其他說法（例如 `signed in`）由擁有它的領域登記在 `SUCCESS_OUTCOMES`，沒有登記就失敗。成功的那幾列訊息欄是空的 |
| `nothing is written` | Then | 請求前後，所有資料表的內容完全相同 |
| `no audit row is written` | Then | 稽核表沒有多出任何一列（其他資料表不管） |
| `an audit row "<類型>" is written` | Then | 稽核表剛好多出一列這個類型 |
| `an audit row "<類型>" is written with actor "<名字>"`、`… with actor SYSTEM` | Then | 同上，而且那一列的行為者是這個帳戶（名稱與帳戶 id 都相符）；`SYSTEM` 是沒有帳戶 id、名稱為 `SYSTEM` |
| `exactly <N> audit row(s) "<類型>" is/are written`，可接 `with actor …` | Then | 稽核表剛好多出 N 列這個類型 |
| `audit rows "<類型一>" and "<類型二>" are written` | Then | 兩個類型各剛好多出一列 |
| `nothing else is written` | Then | 除了前面的步驟已經斷言過的稽核列，資料庫沒有其他差異 |
| `nothing is written except an audit row "<類型>"`，可接 `with actor …` | Then | `an audit row … is written` 加上 `nothing else is written` |

「寫入」的比較忽略 `tests/support/recorder.py` 的 `IGNORED_COLUMNS` 列出的欄位（目前只有
`sessions.last_used_at`）。

稽核列的其他說法（`… naming "…"`、`… with the old and new value`、
`the audit row has the Taipei time …`）各只出現在一個領域，由那個領域定義；它們應該
呼叫 `world.assert_audit_rows_written(…)`，這樣 `nothing else is written` 才知道哪些
列已經斷言過。

## 防護

- 同一句步驟不能被兩個定義比對到：`tests/unit/test_spec_runner.py` 把規格的每一句
  步驟（Examples 的值代入後）對所有定義比對一次，有兩個以上就失敗。pytest-bdd 自己
  遇到這種情況只會默默挑一個。
- 同一個句型在兩個模組各定義一次，在收集測試時就失敗（`tests/steps/__init__.py`）。
- 規格的標籤（`@IAM-F01`、`@money` …）不會變成 pytest 的 mark。
- 下面的清單與規格不一致時測試會失敗；規格的步驟有增減時執行
  `python -m tests.support.spec` 重新產生。
