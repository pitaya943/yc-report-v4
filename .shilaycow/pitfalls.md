# Pitfalls

What went wrong in earlier tasks that would go wrong again. Read this before
building. Each entry: what happened, how to avoid it, how many times it has
happened. At most 30 entries; `shilaycow-retro` proposes changes after each
task and the next task writes them in.

## 1. A list of differences written from memory missed some

- What happened: `spec-baseline-diff.md` listed the feature-file changes from a
  real `diff` but only summarised the rewritten front page; the verifier found
  four wording differences it did not list (system-design, pull request 5,
  finding 1).
- Avoid: when a document claims "these are all the differences", produce the
  list from a diff of every file involved, including rewritten ones, and paste
  the command.
- Count: 1

## 2. The same number kept by hand in several places, checked in only one

- What happened: the spec totals were written in a comment, the index text,
  nine area indexes and the task map; the check tool compared only the comment
  (system-design, pull request 5, finding 2).
- Avoid: a number that appears in more than one place is generated by a tool
  or checked by one, everywhere it appears.
- Count: 1

## 3. `git add -A` staged the builders' worktrees

- What happened: builder worktrees live under `.claude/worktrees/` inside the
  repository and were committed as embedded repositories (system-design,
  commit `39ae504`).
- Avoid: stage by path, and read `git status --short` before committing while
  builders are running. `.gitignore` now covers that directory; do not rely on
  it for other scratch directories.
- Count: 1

## 4. Trail rows stamped with estimated times

- What happened: trail rows carried times ahead of the real clock and had to
  be corrected to the commit times (system-design).
- Avoid: take the time from `date -u` when writing a row, never from an
  estimate.
- Count: 1

## 5. A design section written before its spike returned had to be reversed

- What happened: the design draft fixed the scheduler trigger before the spike
  on that question had finished, and the spike reversed it (system-design,
  ticket T-02).
- Avoid: where a question is still open (a spike, or something only a running
  environment can settle), write that part of the design as the question and
  its candidates, and decide after the result.
- Count: 1
