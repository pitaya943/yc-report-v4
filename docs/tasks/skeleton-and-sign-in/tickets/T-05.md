## Behaviours to prove

1. `create-owner` on an empty system creates the one OWNER, who can then sign
   in; run again it is refused; the password is read without echo, is not
   accepted as a command-line argument, and appears in no output and no audit
   row.
2. `seed-demo` loads the nine accounts of the spec's shared background and is
   refused when `APP_ENV=production`.
3. `/status` shows the four states for an administrator, is FORBIDDEN for a
   USER and UNAUTHENTICATED without a session.
4. The browser test drives a really started server through: choose a group,
   choose a name, sign in, see the landing page with the person's name, sign
   out, and see 「您已登出」. With the sign-out route broken it fails.
5. The start sequence the image uses is proven without a container: with
   production settings and an empty database, `python -m app serve` migrates
   and then answers `/health` with 200; with `DATABASE_URL` removed it exits
   non-zero naming the setting.
6. The Dockerfile is at least syntactically sound and its `COPY` sources all
   exist. No container image can be built in this environment (there is no
   Docker daemon); say so plainly in the Ready comment and do not report the
   image as proven. The image job in the workflow is how it will be proven
   (issue 7).
7. The try-it skill's steps work as written when followed from a clean
   checkout.
