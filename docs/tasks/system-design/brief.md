# Task brief：system-design（系統設計與規格基準）

狀態：草稿，等待 owner 核准。核准前不會開始無人值守的工作。

這是「在本 repo 重建員工日報系統」的第一個 task。整個系統太大，不適合當成一個
task；本 task 的交付物是設計本身，之後的 task 才逐塊建置（見「後續 task 地圖」）。

## 目標

任務完成後，owner 手上有：

1. 一份放在本 repo、可以單獨閱讀的行為規格基準：以 yc-daily-report-v3 的規格為
   本，併入 v3 之後才做出的修正，並補上 v3 遺漏而重建時一定會碰到的決定。
2. 一份取捨紀錄：四個舊系統（v1 daily-report-system、yc-daily-report-system、
   v2、v3）各自哪些做法被採用、哪些被捨棄，以及原因。
3. 一份系統設計：這次要怎麼建，為什麼這樣建，另一種做法是什麼。
4. 四個高風險環節已在本機實際試過的證據，而不是留到後面才發現做不出來。
5. 一張後續 task 地圖，讓 owner 能逐個 task 交辦與驗收。

## 不做什麼

- 不建置任何使用者功能（登入、日報、薪資等都屬於後續 task）。
- 不部署，不連線任何真實的 Supabase、Railway、Cloudflare R2 或其他正式服務。
- 不使用任何真實員工資料、真實銀行帳號或真實金鑰。
- 不改變商業規則。規格基準與 v3 原文不同的地方，只限 v3 自己後來的決定，以及
  本 brief「假設」列出的補洞；每一處都要列出來源。
- 風險試作的程式碼不當成產品程式碼合併；只留下做法、結果與重現步驟。
- 不沿用舊 repo 的流程規則（CI 政策檢查、路徑白名單、角色名稱等）；流程由本
  repo 的 shilaycow 設定決定。

## 情境

本 repo 目前沒有 `docs/spec/`，以下情境全部是新增。

**S-1 規格基準可以單獨閱讀**
- Given 一位沒看過任何舊 repo 的人
- When 他只讀本 repo 的規格
- Then 他找得到 v3 的 9 個能力域、31 個 feature 的全部規則與例子，以及名詞表、
  狀態轉移、欄位限制與錯誤訊息、工項與預設單價

**S-2 規格基準與 v3 原文的每一處差異都有來源**
- Given 規格基準已建立
- When owner 打開差異清單
- Then 每一處與 v3 原文不同的地方都列出：改了什麼、來源是哪一個決定、原因

**S-3 規格的例子可以被工具讀取**
- Given 規格基準裡的全部 feature
- When 執行一個指令做語法檢查
- Then 全部通過，並印出 feature、規則、例子的數量；這些數量與規格首頁寫的一致

**S-4 每個舊系統都有取捨紀錄**
- Given 四個舊系統
- When owner 打開取捨紀錄
- Then 每個系統都列出被採用與被捨棄的做法，各附一句原因，並標明是讀過確認的
  還是推論的

**S-5 設計回答了重建者一定會問的問題**
- Given 系統設計文件
- When owner 讀完
- Then 他知道：用什麼技術建、資料怎麼存（特別是「算過的薪資不會因為後來改設定
  而改變」與「舊日報永遠用送出當時的工項組」這兩件事怎麼保證）、規格的例子怎麼
  變成自動測試、檔案與排程與金鑰在本機怎麼運作；每個重要選擇都寫了另一個選項
  與代價

**S-6 四個高風險環節都實際試過**
- Given 四個環節：(a) 上傳檔案並產生會過期的下載連結、(b) 由可控制的時鐘觸發
  每日與月底的自動歸檔、(c) 銀行帳號加密，以及金鑰不存在時系統仍可運作且不存
  明文、(d) 產生含繁體中文的 PDF 與銀行轉帳格式的 Word 檔
- When owner 照紀錄的步驟在本機執行
- Then 每個環節都看得到成功的結果；做不到的環節則寫明卡在哪裡與替代做法

**S-7 懸而未決的問題都有預設答案**
- Given 舊 repo 留下的未回答問題（v3 的 7 個規格問題、容量與回應時間的數字、
  真實的預設材料清單、銀行轉帳範例檔），以及 v2 有而 v3 沒帶過來的規則
- When owner 打開問題清單
- Then 每一題都有一個已選定的預設答案、選它的理由、以及之後改答案會影響哪些
  後續 task

**S-8 後續 task 地圖涵蓋整個系統**
- Given 後續 task 地圖
- When owner 逐一核對
- Then 31 個 feature 每一個都恰好屬於一個後續 task；每個 task 寫明涵蓋的
  feature、例子數量、依賴哪些 task、哪些可以同時進行

## 怎麼試

1. 打開 `docs/tasks/system-design/` 與 `docs/spec/`，依 S-1、S-2、S-4、S-5、S-7、
   S-8 逐項對照文件內容。
2. 執行報告裡給的語法檢查指令，確認結果與規格首頁的數量一致（S-3）。
3. 依報告裡每個風險試作的重現步驟在本機執行，確認看得到結果（S-6）。

## 預算

4 小時、12 個 session（設定檔預設值；一個 subagent 算一個 session）。

## 謹慎程度

一般。

## 假設

以下是 owner 沒有明說、我先選定的預設；核准 brief 即表示同意，或請直接改。

1. 「模擬建置」的意思：在本 repo 建出真的能在本機執行、能通過規格例子的系統，
   使用拋棄式的本機資料庫與本機檔案儲存；不部署、不碰正式服務與真實資料。
2. 規格以 v3 為準。v1、v2 與 v3 不一致時採 v3；v3 的規格與它自己後來的決定不
   一致時採較新的決定。
3. 規格基準沿用 v3 的語言規約：說明用繁體中文，Gherkin 關鍵字與步驟用英文，
   使用者看得到的字串保留繁體中文。
4. 技術選擇屬於設計的一部分，由本 task 決定並寫明理由。目前傾向沿用 v3 已驗證
   到日報階段的組合（Python、FastAPI、伺服器端頁面、PostgreSQL），但改用專屬的
   本機資料庫，不與任何既有專案共用。
5. v2 有而 v3 沒帶過來的規則（重複送出的防護、找不到的日報怎麼回應、幾個登入
   與權限相關的訊息）不直接照抄，而是在 S-7 各選一個預設答案。
6. 銀行轉帳範例檔與真實材料清單拿不到時，以 v1 的版型與 94 筆材料種子資料
   代替，並在問題清單註明是替代品。
7. 容量目標沿用 v3 的寫法（舊規模的 10 倍，約 850 個帳戶、每月約 18,700 筆
   日報）；回應時間門檻沒有數字，本 task 先提出建議值，不當成驗收條件。
8. 規格基準放在 `docs/spec/`，讓 shilaycow 的其他 skill 找得到。
