# 舊系統取捨紀錄

四個舊 repo 各自哪些做法這次採用、哪些捨棄。每一列標明依據：**讀過**表示在該 repo
的檔案裡讀到；**推論**表示由讀到的事實推得，沒有直接證據。

分析方式：三個唯讀的子代理分別讀完 v3 的建置紀錄、v2 的規格與建置報告、v1 與
harness repo，Chief 自己讀 v3 的規格本體；以下是彙整後的結論。讀取的版本：
v1 `aaf95f3`、yc-daily-report-system `f79726f`、v2 `9b5ed2f`、v3 `e839d9d`。

## 總覽

| 系統 | 是什麼 | 做到哪裡 | 這次的角色 |
| --- | --- | --- | --- |
| v1 `daily-report-system` | 實際上線過的 Flask 單檔系統（`app.py` 6,181 行） | 功能最完整，但有數個計算與資料一致性的缺陷 | 參考資料與部分公式的對照來源 |
| `yc-daily-report-system` | 只有流程規則的 repo，沒有產品程式 | 無 | 取三條測試規則 |
| v2 `yc-daily-report-v2` | Next.js + NestJS + PostgreSQL 的重寫 | 登入、日報、確認、份額（M1、M2），未部署 | 資料形狀與並行處理的經驗 |
| v3 `yc-daily-report-v3` | 規格重整為 Gherkin，FastAPI 重寫 | 登入、日報（40 張 ticket 做完 16 張），未部署 | 規格基準與主要的做法來源 |

## v3 `yc-daily-report-v3`

| 做法 | 取捨 | 原因 | 依據 |
| --- | --- | --- | --- |
| 行為規格（全部的 feature）與之後的修正決定 | 採用 | owner 已同意其規則；是四個版本中唯一把每條規則寫成可執行例子的 | 讀過 `spec/`、`docs/decisions.md` |
| 規格的 feature 檔直接當測試，依規則 ID 逐步開啟（`tests/implemented.txt`） | 採用 | 規格與測試不會分岔；未建置的規則不必寫 skip，CI 從第一天就是綠的 | 讀過 `tests/test_spec.py`、`tests/support/bdd_plugin.py` |
| 小核心：統一的拒絕出口（結果類別對應 HTTP 狀態）、稽核寫入的兩種交易模式、失敗即拒絕的權限檢查、唯一的時鐘來源、存雜湊的 session 與標頭式 CSRF | 採用 | 每個只有 60 至 240 行，卻擋住最多錯誤；規格的拒絕三斷言靠它們成立 | 讀過 `app/core/` |
| 純函式的計算（小組分配、薪資、保留金、匯入比對），整數 tenth 與 `Fraction`，half-up 自己實作 | 採用 | Python 的 `round()` 是銀行家捨入，v3 踩過；純函式可以直接對規格的例子表 | 讀過 `app/domain/`、`docs/pitfalls.md` |
| 「資料沒有任何變動」用操作前後的全表快照比對 | 採用 | 是規格拒絕案例第三個斷言最直接的證明 | 讀過 `tests/conftest.py` |
| 測試從規格檔解析固定資料與錯誤字串，而不是另外抄一份 | 採用 | 字串只有一個來源，抄錯會立刻變紅 | 讀過 |
| 純 SQL 的編號 migration，不用 ORM | 採用 | 並行靠列鎖，SQL 直寫最清楚；v2 也是同樣結論 | 讀過 `migrations/`、D-012 |
| 禁止資料庫函式、trigger 與 `DO` 區塊（D-045） | **捨棄** | 這條是為了讓「migration 只動自己 schema」的掃描器好寫；專屬資料庫沒有這個需求，而稽核不可改、庫存不變式正適合用資料庫約束保證 | 讀過 D-045；適用性是推論 |
| 約 800 行的 CI 政策檢查、447 行的 SQL 範圍分析、本機網址防護、逐 ticket 的路徑白名單 | **捨棄** | 幾乎全部源自「與舊系統共用同一個 Supabase 專案」與「不信任 builder」；M0 兩張基礎 ticket 各修了 2 輪。改用專屬資料庫後不需要 | 讀過 `docs/ci-checks.md`、M1 與 M2 報告；因果是推論 |
| 「測試不得被弱化」以測試 ID 比對結果，因此禁止改名 | **捨棄** | 多次擋住正當的工作（分支落後、規格更動），還衍生出 D-103 的固定流程 | 讀過 D-046、D-052、D-103 |
| 共用的測試步驟邊做邊補 | **捨棄，改為先設計** | M2 四次停工都源自共用步驟太嚴或太窄。這次在骨架 task 一次對著全部 feature 設計「結果」「稽核」「沒有其他寫入」三類步驟 | 讀過 `docs/milestones/M2.html` |
| 每個 feature 一個資料夾，各自 router/service/repo | **捨棄，改為每個領域一個套件** | 為了讓路徑白名單不重疊才切這麼細，結果 feature 之間互相匯出函式 | 讀過 `app/modules/`；原因是推論 |
| 檔案儲存、排程、加密、PDF 與 Word 全部排在最後的里程碑 | **捨棄，改為先試作** | 這四件事到專案停止都沒被驗證過；本 task 的 T-01、T-02 先做 | 讀過 `docs/board.md` |
| 每個測試清空資料庫，密碼雜湊用正式強度 | **捨棄** | 1,218 個測試要約 5 分鐘，而只開了 27 條規則。改用範本資料庫與測試專用的雜湊參數 | 讀過 M2 報告；改善幅度是推論 |
| 並行測試只送 2 個請求 | **捨棄** | 拿掉鎖之後 15 次只失敗 10 次；這次要求拿掉防護後每次都失敗 | 讀過 M2 報告 |
| 瀏覽器層只有驗證者臨時跑的 Playwright | **捨棄，改為納入 CI 的冒煙測試** | 有兩個畫面缺陷 pytest 抓不到 | 讀過 M2 報告 |
| 工項目錄寫成程式常數 | 採用，但單價放資料庫 | 目錄是規格附錄 A 的固定內容；單價可由管理員修改 | 讀過 M2 報告第 6 節 |

## v2 `yc-daily-report-v2`

| 做法 | 取捨 | 原因 | 依據 |
| --- | --- | --- | --- |
| 日報、明細（整數 tenth）、作業小組（含順序）、份額的資料形狀 | 採用 | 正好符合 AD-4（日報記下工項組）與 AD-7（小組在送出時凍結） | 讀過 `supabase/migrations/` |
| 帳戶的資料庫約束：大表旗標只限 USER、owner 不可封存、只允許一位 owner 的部分唯一索引 | 採用 | 把規格的不變式交給資料庫保證 | 讀過 |
| 登入嘗試存在資料庫裡做頻率限制 | 採用 | 多個行程也成立；v1 的記憶體計數在多行程下失效 | 讀過 |
| 編輯、刪除、確認以列鎖序列化，附 24 輪的競態測試 | 採用 | v2 實際踩到「編輯與確認同時發生，留下已確認卻過時的份額」 | 讀過 `docs/reports/T-203.md` |
| 一次性的送出憑證，防止同一張表單送兩次 | 採用想法，補上期限 | v2 的重複日報是真的發生過的缺陷；v2 的憑證沒有期限。見 `open-questions.md` OQ-8 | 讀過 B-062、`docs/decisions.md` |
| 安全教訓：不信任轉送的來源位址；延長 session 時兩個 cookie 都要重發 | 採用 | T-102 為此做了三輪 | 讀過 `docs/reports/T-102.md` |
| Next.js + NestJS 兩層，加上共用的 Supabase 專案 | **捨棄** | 兩層之間的代理讓頻率限制的來源位址可被偽造，另有兩個 cookie 缺陷；而 Supabase 的 Auth、RLS、Storage 一項都沒用到。沒有與單層做法的對照實驗，所以「單層較好」是推論 | 讀過報告；比較是推論 |
| 前端測試檢查原始碼字串，不經瀏覽器 | **捨棄** | 重複送出與頁數顯示的缺陷都是驗證者才抓到 | 讀過 `docs/reports/T-203.md` |
| 稽核表只記顯示名稱，而且應用程式的資料庫角色可以改刪 | **捨棄** | 違反「稽核不可修改」；改名後也對不回帳戶 | 讀過 migration |
| 逐欄位的 `file:line` 引用清單、資料表清單的完全比對測試 | **捨棄** | 每次 migration 都壞，還需要專門的修補 ticket | 讀過報告 |
| 被 v3 推翻的規則（不合格的共同作業者直接略過、可改回報日期、錯誤一律 400） | **捨棄** | v3 較新，owner 已同意 | 讀過 D-097、AD-8、AD-9 |
| 英文的暫用介面文字 | **捨棄** | 不是規格的字串 | 讀過 |
